### 3. 50 个测试案例应该怎么准备

题目没有规定六个场景如何分配，也没有要求平均分配。建议用下面的覆盖方式：

| 场景 | 建议案例数 |
|---|---:|
| 生日与节日问候 | 8 |
| 产品推荐 | 9 |
| 购后关怀 | 8 |
| 沉睡客户唤醒 | 8 |
| 活动邀请 | 8 |
| 价格异议 | 9 |
| **合计** | **50** |

不要只测试“资料完整、容易回答”的情况。建议穿插：

- 客户信息缺失、历史对话很少。
- 客户明确拒绝购买或表达不满。
- 产品信息不足，不能随意编造材质、库存、功效。
- 要求折扣，但品牌政策不允许。
- 历史偏好与本次产品不匹配。
- 客户不希望频繁被打扰。

每个案例必须使用题目指定的列：

`Case ID | Scenario | Client information | Conversation history | Product information | Output 1 | Output 2 | Output 3`

**这些输出应由工具实际生成。** 如果做了人工修改，建议另列说明，不要将修改后的文案当作原始生成结果。

### 4. 最终必须提交哪些内容

题目明确要求 **A—E 五项**：

| 必交项 | 你需要写什么 |

| **C. 50 test cases：测试案例** | 50 组完整输入，以及每组工具生成的 3 条消息 |
| **D. Evaluation report：评估报告** | 对输出的评价及截图。建议包含整体结果、各场景表现、典型成功和失败案例 |
| **E. Defects and next steps：缺陷与后续计划** | 发现的问题、做过的修改、修改前后对比、待优化问题；修改后要注明结果来自哪个版本 |

建议将评价标准分成两类，方便解释：

- **质量评分**：个性化、品牌一致性、中文自然度、场景适配、三条候选的差异性。
- **不可接受项**：编造产品事实或优惠、违背客户明确意愿、冒犯客户、泄露信息、未生成规定数量的消息等。

这些具体标准由你定义，但需要在报告中说明理由。
